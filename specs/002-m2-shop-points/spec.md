# Feature Specification: M2 营收 — 积分体系 + 商城全链路 + 后台最小集

**Feature Branch**: `002-m2-shop-points`

**Created**: 2026-10-24

**Status**: Draft

**Input**: User description: "M2 营收：积分账本（余额+流水+对账）、商品/分类（库存/促销/SKU 校验）、购物车、结账（角色校验+积分支付+SOAP 发货+状态闭环）、9+ 服务处理器、后台商品/订单/用户/积分手调、商城存量迁移（订单清洗+图片上 COS）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 积分账本完整域 (Priority: P1)

玩家的一切积分变动（消费扣减、注册/徽章奖励、管理员手动调整）都以流水入账，余额随时可由流水重算推导；系统提供对账机制，任何账实差异可见、可查、可清零。积分页向玩家完整展示余额与全部流水。这是结账支付的账务地基，也是宪法原则 III（账本可重算）的完整落地。

**Why this priority**: 支付扣减是营收链路的第一笔账；账本不可信则商城不可上线。

**Independent Test**: 对测试账号执行入账/扣减/手动调整各一笔，断言每笔产生流水、余额=流水累加；把余额改为错误值后跑对账，差异清单能准确点名该账户。

**Acceptance Scenarios**:

1. **Given** 余额 100 的账号，**When** 购买 60 积分商品支付成功，**Then** 产生一条消费流水（余额快照 40）且余额变为 40
2. **Given** 余额 10 的账号，**When** 尝试支付 60 积分商品，**Then** 支付被拦截并提示余额不足，不产生任何流水与订单
3. **Given** 管理员手动调整某用户 +50 积分并填写原因，**Then** 产生 manual 类型流水，记录操作者与原因
4. **Given** 某账户余额被直接篡改（模拟事故），**When** 对账任务运行，**Then** 差异清单准确列出该账户的重算值与现存值
5. **Given** 登录用户访问积分页，**Then** 看到真实余额与全部分页流水（时间/类型/数额/备注）

### User Story 2 - 商城浏览与购物车 (Priority: P1)

玩家访问 `/shop` 浏览商品：分类筛选、价格排序、分页；进入商品详情查看图集/描述/价格（促销价划线展示）与 Wowhead 物品浮窗；加购前选择名下游戏角色（物品类与服务类均需）；购物车内调整数量、移除、逐行复核下单参数。未登录用户加购/结账被引导登录。

**Why this priority**: 商品浏览与购物车是结账的前半程；角色选择组件是"下单绑定角色"铁律的入口。

**Independent Test**: 用测试商品走通 列表筛选→详情→选角色→加购→购物车复核→移除 全流程；断言越权选择他人角色被服务端拒绝。

**Acceptance Scenarios**:

1. **Given** 商品已按分类上架，**When** 玩家在 `/shop` 选择分类/切换排序/翻页，**Then** 结果正确响应
2. **Given** 物品类商品详情页，**When** 玩家悬停物品图标/名称，**Then** 展示 Wowhead 物品浮窗
3. **Given** 已登录玩家在详情页加购，**When** 选择名下某角色，**Then** 该选择随购物车行保存并在购物车页可见
4. **Given** 未登录访客，**When** 点击加购或结账，**Then** 被引导至登录页
5. **Given** 购物车内有物品类与服务类商品各一，**When** 玩家查看购物车，**Then** 每行展示各自下单参数（角色名/所选恢复物品/目标账号等）供复核

---

### User Story 3 - 结账支付与发货状态闭环 (Priority: P1)

玩家从购物车发起结账：强制登录、确认订单行参数、积分支付。系统在同一事务内完成扣积分+订单创建+库存扣减，随后经命令通道发货，发货成功订单自动推进至已完成（修复旧系统 1,895/1,897 单滞留 processing 的缺陷）；发货失败进入可见的失败状态与重试队列，支持人工补发。玩家在用户中心可查看订单列表与详情（含状态与发货结果）。

**Why this priority**: 这是本里程碑的核心验收锚点（下单→扣分→发货→completed 全链路），也是宪法原则 II（发货必须可靠可见）的主战场。

**Independent Test**: 在测试环境用测试商品完整下单，断言：积分扣减流水、库存扣减、命令通道发货调用、订单自动 completed 四步全部发生且一致；注入发货失败，断言订单进入失败态、可从后台补发成功。

**Acceptance Scenarios**:

1. **Given** 余额充足的登录玩家，**When** 对库存充足的商品完成结账，**Then** 积分被扣减、库存被扣减、发货命令已执行、订单自动变为已完成——全程无人工介入
2. **Given** 发货命令执行失败（超时/服务不可用），**When** 支付已完成，**Then** 订单进入明确的发货失败状态，重试队列可见，管理员可人工补发，补发成功后订单变为已完成
3. **Given** 玩家在结账时提交了不属于本人的角色，**When** 服务端校验，**Then** 请求被拒绝并记录越权审计
4. **Given** 库存仅剩 1 件的限量商品，**When** 两个玩家同时购买，**Then** 仅一个成功，另一个得到售罄提示，库存不超卖
5. **Given** 订单被管理员退款，**When** 退款执行，**Then** 积分全额回补（产生流水）且库存回补，订单状态留痕
6. **Given** 登录玩家访问用户中心订单页，**Then** 可见订单列表与详情（条目/积分金额/状态/发货结果/下单参数）

---

### User Story 4 - 服务类商品处理器 (Priority: P2)

9+ 种服务类商品（改名/改阵营/改种族/改外观单件/幻化套装/外观重置/装备恢复/角色转移/角色复制/公会变更/名字解锁）经统一处理器执行：每类商品在商品页采集专属参数、结账复核、随订单行落库、发货时由对应处理器执行命令。装备恢复商品需先选角色再异步加载可恢复物品单选（与用户中心物品恢复同源）。

**Why this priority**: 商城营收的差异化主力，但依赖 US3 的发货框架先行就绪。

**Independent Test**: 每类服务商品在测试环境走通"参数采集→校验→下单→发货执行"链路；参数缺失（如未选恢复物品）时加购/结账被拦截。

**Acceptance Scenarios**:

1. **Given** 角色转移商品，**When** 玩家选择角色并填写目标账号名，**Then** 服务端校验目标账号存在后允许下单，发货时执行转移
2. **Given** 装备恢复商品，**When** 玩家选定角色，**Then** 异步加载该角色可恢复物品列表（浮窗展示物品名/图标）供单选；未选物品不得加购
3. **Given** 装备恢复商品订单支付前，**When** 游戏服务器离线，**Then** 支付被拦截并提示
4. **Given** 名字解锁商品，**When** 玩家提交全小写名字，**Then** 系统规范化为首字母大写并校验合法性与占用后受理
5. **Given** 公会变更商品，**When** 玩家提交非法公会名，**Then** 被服务端拒绝
6. **Given** 任意物品类商品，**When** 玩家尝试指定"寄给其他角色"，**Then** 系统不提供该能力（决策 D6：物品一律寄下单所选角色）

---

### User Story 5 - 运营后台最小集 (Priority: P2)

管理员在后台维护商品（含 SKU 映射保存校验：物品类 ID 必须在游戏物品库存在、服务类必须绑定已注册处理器）、促销价与档期、库存与缺货/低库存阈值、上下架与目录隐藏；处理订单（查看/手动补发/退款）；管理用户（列表/积分手动调整/徽章授予/邀请码批量生成与停用）。后台仅管理员角色可达，越权访问记审计。

**Why this priority**: 上线运营的最低自持能力——没有后台，发货失败无法补、商品无法自主维护。

**Independent Test**: 管理员新增一个物品类商品（合法与非法 SKU 各一），断言非法被拒；对一笔失败订单执行补发；给用户手动调整积分并断言流水产生。

**Acceptance Scenarios**:

1. **Given** 管理员保存物品类商品，**When** SKU 引用的游戏物品 ID 不存在，**Then** 保存被拒并说明原因
2. **Given** 管理员设置促销价与档期，**When** 档期内用户下单，**Then** 按促销价成交；档期结束自动恢复原价
3. **Given** 商品库存降至低库存阈值，**Then** 管理员收到提醒；降至 0 自动转缺货，前台置灰禁购但仍可见
4. **Given** 一笔发货失败订单，**When** 管理员点击补发，**Then** 发货重新执行且全程留痕
5. **Given** 普通登录用户，**When** 直接访问后台任意页面，**Then** 被拒绝并记审计
6. **Given** 管理员批量生成邀请码并停用其中一个，**Then** 列表状态与使用记录可查（注册侧消费启用随后续迭代）

### User Story 6 - 商城存量数据迁移 (Priority: P3)

旧系统商城数据迁入新系统：99 个商品+14 分类（含双价模型与库存配置）、1,897 笔订单+3,055 条目（状态按确认口径清洗，绑定角色从订单 meta 还原）、图片资产（uploads 4.4G）上对象存储+CDN 并全站 URL 重写。迁移完成后积分对账差异清零。

**Why this priority**: 迁移是切换上线的前置，但机制与前台链路先行；商品数据可先小规模试迁支撑开发。

**Independent Test**: 试迁后核对：商品数量/价格/分类与旧库一致；订单清洗结果按口径分布正确；抽样 20 户积分余额与前端展示一致；抽样页面图片全部可达。

**Acceptance Scenarios**:

1. **Given** 旧库商品全量导出，**When** 执行迁移，**Then** 99 商品+14 分类落库，SKU 映射校验全部通过
2. **Given** 1,897 笔存量订单，**When** 按 D3 口径清洗导入（有扣分流水+发货标记→已完成；扣分与金额不符→单列人工复核；无扣分流水→已取消），**Then** 各状态分布与口径一致，滞留 processing 缺陷不再复现
3. **Given** 迁移完成，**When** 执行全量积分对账，**Then** 差异以存量余额为准逐户补录调整流水抹平，抹平后重算差异清单清零，抽样 20 户前端展示一致
4. **Given** 图片资产上传对象存储后，**When** 访问抽样存量页面，**Then** 图片经新 CDN 地址全部可达，死链扫描归零

### Edge Cases

- 发货命令超时但游戏端实际已执行：幂等键保证补发不产生重复发货（宁可人工核对审计，不可重复发物品）
- 支付事务成功但发货通道不可用：订单停留失败态可补发，绝不回滚扣分（扣分已发生则账实必须一致）
- 并发扣减库存至临界值：事务内扣减，不超卖；并发支付同一账户余额临界值：不透支
- 服务类商品订单行参数缺失/被篡改：发货处理器前置校验拒绝执行并告警，不发货
- 促销档期边界（开始瞬间/结束瞬间）：以服务端结算时刻的生效价为准
- 对象存储不可用：商品图回退占位图，页面不白屏；恢复后自动可达
- 游戏库临时不可达：商品页角色下拉降级提示，不阻塞浏览；结账被拦截
- 迁移中断重跑：幂等导入，不产生重复商品/订单/流水
- 清洗出"扣分与金额不符"的存量订单：单列人工复核清单，不静默归入任何状态

## Requirements *(mandatory)*

### Functional Requirements

**积分账本**

- **FR-101**: 一切积分变动必须以流水入账并在同事务更新余额，流水携带余额快照；任意时刻余额必须等于该用户全部流水之和（可重算不变式）
- **FR-102**: 消费扣减必须先校验余额，不足拦截并明确提示；扣减流水类型独立可辨（对应存量 woocommerce_payment）
- **FR-103**: 流水类型枚举必须覆盖存量 6 类（注册奖励/徽章奖励/商店消费/定期发放/手动调整/访问推荐）并与旧系统 ref 值一一映射
- **FR-104**: 积分获取必须经规则表驱动（事件→规则），新增/调整加分规则不修改代码；商店支付扣减为固定账务路径不经规则表
- **FR-105**: 手动调整必须记录操作者与原因，流水可追溯到管理员
- **FR-106**: 系统必须提供对账能力：按流水重算逐户比对现存余额，产出差异清单；支持迁移期全量对账与日终定时对账双保险
- **FR-107**: 积分页展示余额与全部分页流水（时间/类型/数额/备注）

**商城前台**

- **FR-108**: 商品分两类模型：物品类（关联游戏物品 ID）与服务类（SKU 为处理器路由键）；商品归属分类树（对应存量 14 分类）
- **FR-109**: `/shop` 提供分类筛选、价格排序、分页；商品卡片展示图/名/价/分类；`/shop` `/cart` `/checkout` `/my-account` 路径保持不变
- **FR-110**: 商品详情展示图集/描述/价格/分类归属；物品类支持 Wowhead 浮窗；存在促销价时划线展示原价
- **FR-111**: 禁止游客结账；未登录加购/结账引导登录
- **FR-112**: 购物车支持数量调整/小计/移除；每行展示该商品下单参数供复核
- **FR-113**: 下单必须选择名下游戏角色：角色下拉仅出本人角色（服务端强制归属校验）；所选角色与其它下单参数随购物车行持久化并落订单行
- **FR-114**: 开启库存管理的商品：支付成功事务内扣减库存，订单取消/退款自动回补，扣至 0 自动转缺货禁购；缺货商品前台仍可见并标记售罄
- **FR-115**: 商品支持原价+促销价双价模型与可选促销档期；结算一律取服务端判定的当前生效价

**结账与发货**

- **FR-116**: 订单状态机必须闭环：待支付→已支付→发货中→已完成（自动推进）；发货失败→发货失败态（可重试/可人工补发）；退款/取消→回补积分与库存并留痕。禁止发货后订单无终点滞留
- **FR-117**: 支付扣分+订单创建+库存扣减在同一事务完成；命令通道发货在事务外执行，携带幂等键，每次调用（含失败）审计留痕
- **FR-118**: 发货失败必须可见：订单明示失败态、进入重试队列、后台提供人工补发入口；发货结果回写订单行
- **FR-119**: 服务端必须在结账与发货前强制校验角色归属，越权请求拒绝并记审计
- **FR-120**: 装备恢复类商品支付前必须校验游戏服务器在线；未选恢复物品不得加购与结账
- **FR-121**: 用户中心提供订单列表与详情（条目/积分金额/状态/发货结果/下单参数）

**服务类处理器**

- **FR-122**: 服务类商品按策略模式注册处理器（改名/阵营/种族/外观单件/幻化套装/外观重置/装备恢复/角色转移/角色复制/公会变更/名字解锁）；SKU 未绑定已注册处理器不得保存与发货
- **FR-123**: 各服务专属参数在商品页采集、购物车/结账复核、随订单行落库、发货时经处理器前置校验后执行（目标账号存在性/公会名合法性/解锁名规范化与占用等）
- **FR-124**: 物品类商品一律寄送至下单所选角色，不提供"寄给他人角色"能力（决策 D6）

**运营后台**

- **FR-125**: 权限模型为游客/用户/版主/管理员四角色；后台仅管理员可达，越权访问记审计
- **FR-126**: 后台商品保存必须校验 SKU 映射：物品类 ID 在游戏物品库存在、服务类绑定已注册处理器，非法拒绝保存
- **FR-127**: 商品支持上下架/草稿/目录隐藏；下架不影响历史订单展示
- **FR-128**: 缺货/低库存阈值可配置；库存降至阈值提醒管理员
- **FR-129**: 后台订单管理提供列表/详情/手动补发/退款；退款自动回补积分（产生流水）与库存并全程留痕
- **FR-130**: 后台用户管理提供列表/积分手动调整/徽章授予/邀请码批量生成与停用（状态机与使用记录可查）

**存量迁移**

- **FR-131**: 商店存量（99 商品/14 分类/1,897 订单/3,055 条目）按 D3 口径清洗导入（决策 2026-10-24）：有扣分流水且有发货标记→已完成；扣分流水与订单金额不符→单列人工复核清单；无扣分流水→已取消；绑定角色从订单 meta 还原；导入幂等可重跑
- **FR-132**: 图片资产迁至对象存储+CDN，全站 URL 重写映射，死链扫描归零；对象存储配置按宪法原则 VI 存业务库配置表
- **FR-133**: 迁移后必须全量积分对账，差异裁决以存量余额为准（决策 2026-10-24）：逐户补录调整流水抹平差异，抹平后流水重算差异清单清零，此后新系统保持余额=流水不变式；抽样 20 户余额与前端展示一致

### Key Entities *(include if feature involves data)*

- **商品**: 类型（物品类/服务类）、SKU、名称、图集、描述、分类归属、原价、促销价+档期、库存开关与库存量、缺货/低库存阈值、上下架/草稿/目录隐藏状态、限购标记（二期）
- **商品分类**: 分类树（对应存量 14 分类）
- **订单**: 状态机（待支付/已支付/发货中/已完成/发货失败/已取消/已退款）、支付流水引用、发货审计引用；订单行含商品快照、成交价、数量、下单参数（角色/恢复物品/目标账号等）与发货结果
- **积分账户/流水**: 余额+流水双记录；流水类型 6 类枚举+余额快照+引用（订单/管理员操作）
- **积分规则**: 事件→分值规则表（注册/徽章等获取类）
- **徽章**: 等级定义+授予记录（授予产生徽章奖励流水）
- **邀请码**: 码值/生成参数/状态机/使用者记录（后台管理先行，注册侧消费后置）
- **图片资产映射**: 旧 URL→对象存储新地址映射表
- **审计事件**: 发货命令调用/补发/退款/越权尝试/后台敏感操作留痕

## 适用宪法原则（合规映射）

- **原则 I 账号一致性三铁律** → FR-113/FR-119（下单绑定本人角色、归属强制校验）
- **原则 II 发货必须可靠可见** → FR-116/FR-117/FR-118（状态闭环、幂等、失败可见可补发；1,895 单滞留教训的正面修复）
- **原则 III 积分账本可重算** → FR-101/FR-103/FR-106/FR-133（余额=流水、类型映射、双保险对账、差异清零）
- **原则 IV 兼容与无感迁移** → FR-109（商店四件套路径不变）/FR-131（存量订单商品迁移，301 已由 M1 覆盖）
- **原则 V 数据边界与生产只读** → FR-126（游戏物品库只读校验）/发货经命令通道而非直写游戏库
- **原则 VI 安全纵深（含配置分域）** → FR-119/FR-125/FR-126（归属/权限/SKU 三重服务端校验）+FR-132（对象存储凭据入配置表不入 env/文档）
- **原则 VII 单体优先 · YAGNI · 明确不做** → 不做清单执行：D6 寄他人角色（FR-124 反向声明）、积分券与订单邮件（已取消）、真实货币网关（仅预留不实现）、定期发放自动复刻（见 Assumptions）
- **原则 VIII 行为变更必有测试** → SC-101/SC-102/SC-105 为自动化验证锚点；下单→扣分→发货→已完成必须有 E2E 覆盖
