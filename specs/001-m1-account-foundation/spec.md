# Feature Specification: M1 地基 — 账号全链路 + 游戏集成 + 路由兼容

**Feature Branch**: `001-m1-account-foundation`

**Created**: 2026-10-23

**Status**: Draft

**Input**: User description: "M1 地基：账号全链路+游戏集成+路由兼容（注册(邀请码)/登录(phpass 无感)/用户中心/游戏四库+SOAP/301 层）"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 存量用户无感登录 (Priority: P1)

现有 6,330 名注册玩家在新系统上线后，使用原有用户名和原密码直接登录，全程无需重置密码、无需人工介入、无任何感知差异。这是本里程碑的核心验收锚点，也是"怀旧公益"社区信任的基石——老玩家一个都不能丢。

**Why this priority**: 登录是一切功能的前提；存量用户凭据迁移失败等于社区迁移失败。

**Independent Test**: 抽取 100 个存量真实账号，逐个用原凭据登录，全部成功且登录后可直接访问用户中心。

**Acceptance Scenarios**:

1. **Given** 一个存量账号（旧系统密码存储格式 phpass），**When** 用户在新登录页输入原用户名和原密码，**Then** 登录成功，进入用户中心，全程无任何额外步骤
2. **Given** 同一存量账号首次登录成功后，**When** 用户再次登录，**Then** 使用升级后的凭据依然登录成功（升级一次性完成，不再回退旧校验）
3. **Given** 一个存量账号，**When** 用户勾选"记住登录"后登录并关闭浏览器，**When** 次日再次访问，**Then** 仍处于登录态

---

### User Story 2 - 新玩家邀请码注册 (Priority: P1)

新玩家凭有效邀请码注册：填写邀请码、用户名（即游戏账号名）、邮箱 → 收到激活邮件 → 经邮件链接进入设密页设置密码 → 账号在站点与游戏端同时创建，即可登录网站和游戏（同密契约）。注册全程密码不出现在注册页。

**Why this priority**: 社区增长入口；注册链路是三条铁律（账号一致性）的第一次完整演练。

**Independent Test**: 用一个可用邀请码完整走完注册→激活→设密→双端登录，并验证邀请码占用、奖励入账、游戏端账号存在。

**Acceptance Scenarios**:

1. **Given** 一个 available 状态的邀请码，**When** 新玩家提交注册（合法用户名+未占用邮箱），**Then** 注册受理成功，收到激活邮件
2. **Given** 已收到激活邮件，**When** 用户经链接进入设密页设置符合复杂度的密码，**Then** 站点用户与游戏端账号同时创建成功，用户可立即登录网站并用同一凭据登录游戏
3. **Given** 一个已过期/已停用/已达上限的邀请码，**When** 用户在注册提交时使用它，**Then** 被实时拒绝并得到明确原因（不依赖后台刷新）
4. **Given** 用户名或邮箱已被站点或游戏端任一侧占用，**When** 用户提交注册，**Then** 被拒绝并提示；含 `@` 的用户名被拒绝
5. **Given** 两个并发请求使用相同用户名注册，**When** 同时提交，**Then** 仅一个成功，另一个收到明确错误，不产生重复账号
6. **Given** 注册完成，**When** 用户查看积分页，**Then** 余额为 +2 且存在一条"注册奖励"流水记录

---

### User Story 3 - 密码找回与修改（双写一致） (Priority: P1)

用户忘记密码时经邮箱重置链接设置新密码；登录用户可在账户设置中修改密码。一切密码变更必须同步写入站点与游戏端，保持两端同密；任一端失败必须可见并处理，禁止静默单边成功。

**Why this priority**: 密码双写是铁律 ② 的主战场；用户自助找回决定运营成本。

**Independent Test**: 分别执行"邮箱找回重置"和"账户设置改密"，验证新密码在网站与游戏端均可登录；模拟游戏端写入失败，验证系统不产生单边不一致且用户得到可见反馈。

**Acceptance Scenarios**:

1. **Given** 一个已注册账号，**When** 用户在找回页提交邮箱并点击邮件中的重置链接设置新密码，**Then** 新密码在站点与游戏端同时生效，旧链接再次使用无效（一次性）
2. **Given** 已登录用户，**When** 在账户设置修改密码，**Then** 双端同步生效
3. **Given** 游戏端写入失败（如临时不可达），**When** 密码变更执行，**Then** 变更不标记完成，进入可见的重试/告警状态，最终一致后用户可正常双端登录

---

### User Story 4 - 用户中心 8 页 (Priority: P2)

登录用户进入用户中心，使用 8 个页面：概览（头像/昵称/角色数/最近动态）、我的角色（名下游戏角色：种族/职业/等级/头像）、积分（余额+流水）、订单（列表+详情）、物品恢复（选角色查看可恢复物品）、RAF 招募进度（只读）、账户设置（昵称/邮箱/密码）、收货地址（地址簿）。

**Why this priority**: 用户中心是后续所有玩家自助服务的容器；角色页是"游戏数据服务"定位的第一次呈现。

**Independent Test**: 用测试账号登录后逐一访问 8 页，角色页仅显示本人角色且信息与游戏内一致；积分/订单页显示空态。

**Acceptance Scenarios**:

1. **Given** 拥有 3 个游戏角色的账号，**When** 用户访问"我的角色"，**Then** 仅显示本人 3 个角色，种族/职业/等级与游戏内一致
2. **Given** 任意登录用户，**When** 访问积分页，**Then** 看到真实余额与流水记录（含注册奖励）；**When** 访问订单页，**Then** 看到页面框架与友好空态（数据随 M2 接入）
3. **Given** 任意登录用户，**When** 访问物品恢复页并选择一个角色，**Then** 看到该角色可恢复物品列表（只读，M2 接入恢复执行）
4. **Given** 未登录访客，**When** 直接访问用户中心任意页面，**Then** 被引导至登录页

---

### User Story 5 - 邀请码后台管理 (Priority: P2)

管理员在后台批量生成邀请码（自定义前缀/长度/数量/每码使用上限/过期时间），查看邀请码列表（状态/已用次数/使用者），启用或停用邀请码。使用者记录以正规关联表存储（修复旧系统字段长度易溢出缺陷）。

**Why this priority**: 邀请码是注册的唯一入口，运营必须能自主发码；后台管理是 P0 M1 需求（需求池已确认）。

**Independent Test**: 管理员生成一批 10 个上限 5 次、7 天过期的邀请码，用一个注册消费后查看占用记录，再停用其中一个并验证其无法注册。

**Acceptance Scenarios**:

1. **Given** 管理员已登录后台，**When** 按参数批量生成邀请码，**Then** 生成成功且参数（前缀/长度/上限/过期）正确落库
2. **Given** 某邀请码已被使用 N 次，**When** 管理员查看列表，**Then** 状态与使用者关联完整可见
3. **Given** 管理员停用一个邀请码，**When** 有人随后用它注册，**Then** 被实时拒绝

---

### User Story 6 - 游戏集成基座（四库 + SOAP 通道） (Priority: P2)

系统与游戏世界建立稳定集成：游戏四库（账号/角色/物品定义/脚本数据）直连（只读为主，账号表按契约写）；游戏服务器命令通道统一封装，具备超时、重试、幂等、审计日志能力——后续商城发货、角色服务全部复用此通道。

**Why this priority**: 这是 M2 商城发货的前置设施；先在 M1 以低风险方式验证通道可靠性。

**Independent Test**: 通过命令通道执行一条只读命令成功返回；模拟超时/失败场景，验证重试与审计留痕完整可查。

**Acceptance Scenarios**:

1. **Given** 游戏服务器在线，**When** 系统执行一条只读查询命令，**Then** 结果正确返回
2. **Given** 命令执行超时或失败，**When** 重试机制触发，**Then** 每次尝试（成功与失败）均有审计记录，可查命令名/参数/结果/耗时
3. **Given** 游戏四库连接配置，**When** 系统启动，**Then** 四库均可连接；除账号表契约字段外对游戏 schema 无任何写操作

---

### User Story 7 - 旧路由兼容层 (Priority: P3)

旧系统 URL 持续可用：登录/注册/找回旧地址整体跳转到新页面；文章/页面类旧地址经映射表 301 到新路径（映射表机制就绪，内容映射随 M3 迁移逐步填充）；商店四件套路径保持不变。教程页截图与外部引用硬编码了旧路径，跳转不可缺失。

**Why this priority**: 上线切换（M4 末）才全面生效，但机制必须在 M1 就绪并先覆盖登录类地址（M1 起新旧并行即被引用）。

**Independent Test**: 访问旧登录/注册/找回地址验证跳转正确；向映射表注册一条测试映射后访问旧地址验证 301；访问未映射旧地址得到 404。

**Acceptance Scenarios**:

1. **Given** 访客点击外部教程中硬编码的旧登录地址（含注册/找回变体），**When** 请求到达，**Then** 被跳转到对应新页面
2. **Given** 映射表中存在 `旧文章地址 → 新文章路径` 条目，**When** 访问旧地址，**Then** 收到 301 并到达新路径
3. **Given** 映射表中无对应条目的旧地址，**When** 访问，**Then** 返回 404（不做模糊猜测）
4. **Given** 商店四件套路径，**When** 访问，**Then** 路径保持不变（M2 内容就绪前显示框架页）

---

### Edge Cases

- 游戏账号库临时不可用时提交注册：注册整体失败并明确提示，站点侧不得产生无游戏账号的"半成品用户"；恢复后可重新提交
- 激活邮件重复点击/过期：设密链接一次性且限时，过期后引导重新发送
- 激活邮件未收到：提供重发入口，有频率限制
- 存量账号凭据异常（个别账号旧哈希损坏）：登录失败给出"找回密码"引导，不得锁死账号，不得影响其他账号
- 邀请码在提交瞬间恰好被用完（并发撞码）：后到者被拒绝并提示，双方账目一致
- 改密时游戏端成功但响应超时：凭审计记录核对，重试不产生重复副作用（幂等）
- 旧地址映射命中但新内容尚未上线：到达新路径的占位页，不白屏
- SOAP 通道重复投递同一条状态变更命令：幂等机制保证副作用仅发生一次

## Requirements *(mandatory)*

### Functional Requirements

**注册与邀请码**

- **FR-001**: 注册必须填写邀请码；提交时实时校验状态机，仅 `available` 可用；`disabled`/`finish`/`expired` 一律拒绝并提示对应原因
- **FR-002**: 邀请码过期必须在提交时刻判定，不得依赖后台列表加载等旁路触发
- **FR-003**: 用户名必须等于游戏账号名，禁止包含 `@` 字符
- **FR-004**: 注册提交时必须实时校验用户名与邮箱在"站点+游戏账号系统"两侧均未被占用，任一侧占用即拒绝
- **FR-005**: 注册页不得出现密码输入；提交后发送激活邮件，用户经一次性限时链接进入设密页完成设密
- **FR-006**: 设密必须强制复杂度校验，弱密码被拒绝并说明规则
- **FR-007**: 注册成功必须同步创建游戏端账号，且游戏端密码与站点密码一致（同密契约 D2）；任一侧失败不得产生半成品账号
- **FR-008**: 注册成功链路必须完整：站点用户创建、游戏端账号创建、注册奖励积分 +2 以正式流水入账（积分账本最小集随 M1 落地：流水记录+余额，且余额必须可由流水重算推导；完整积分域随 M2 扩展），邀请码占用记录（码记录与用户侧关联双向完整）
- **FR-009**: 并发提交相同用户名/邮箱必须仅一个成功，其余得到明确可读错误
- **FR-010**: 激活邮件必须支持重发，且有频率限制

**登录与凭据迁移**

- **FR-011**: 存量用户必须能用原用户名+原密码直接登录成功（兼容存量 phpass 哈希），首次登录成功后自动升级为新哈希格式，用户全程无感
- **FR-012**: "记住登录"行为保持：勾选后获得长会话，期间免重复登录
- **FR-013**: 登录失败提示统一模糊（不泄露"用户存在但密码错"类信息）
- **FR-014**: 密码修改/重置必须双写站点与游戏端；单边失败必须进入可见的重试与告警状态，禁止静默单边成功
- **FR-015**: 找回密码重置链接必须一次性且限时，过期或已用即失效

**用户中心**

- **FR-016**: 用户中心 8 页（概览/我的角色/积分/订单/物品恢复/RAF 招募/账户设置/收货地址）登录后全部可达
- **FR-017**: 我的角色页仅展示登录用户本人的游戏角色（种族/职业/等级/头像），归属由服务端强制校验
- **FR-018**: 积分页 M1 展示真实余额与流水记录（数据源为最小账本）；订单页 M1 交付页面框架与友好空态，数据随 M2 接入
- **FR-019**: 物品恢复页 M1 提供角色选择与该角色可恢复物品列表（只读）
- **FR-020**: RAF 招募进度只读展示
- **FR-021**: 账户设置支持修改昵称/邮箱/密码；邮箱变更需验证新邮箱后生效

**游戏集成基座**

- **FR-022**: 游戏四库（账号/角色/物品定义/脚本数据）连接可用；以只读为默认姿态，仅账号表按契约写入；凭据仅存环境变量
- **FR-023**: 游戏命令通道（SOAP）统一封装：超时、重试、幂等、审计日志；每次调用（含失败）均留痕可查（命令/参数/结果/耗时）
- **FR-024**: 激活/重置等事务邮件发送失败必须可见（重试+告警），禁止静默丢失

**路由兼容**

- **FR-025**: 旧登录/注册/找回地址（`/wp-login.php` 及其 action 变体）必须跳转到新对应页面
- **FR-026**: 基于映射表的旧→新地址 301 机制必须就绪（覆盖 `?cat=`/`?p=`/`?page_id=` 三类），映射未命中返回 404
- **FR-027**: `/shop` `/cart` `/checkout` `/my-account` 路径保持不变

**邀请码后台**

- **FR-028**: 管理员可按参数（前缀/长度/数量/每码上限/过期时间）批量生成邀请码
- **FR-029**: 管理员可查看邀请码列表（状态/已用次数/使用者关联）并启用/停用
- **FR-030**: 邀请码与使用者的关联必须以关联表存储（修复旧系统字符串拼接易溢出缺陷），支持按码查询使用者

### Key Entities *(include if feature involves data)*

- **站点用户**: 用户名（=游戏账号名）、邮箱、密码凭据（含存储格式标记与迁移来源）、状态、注册所用邀请码关联
- **游戏端账号**: 游戏账号系统中的账号，用户名/邮箱与站点一致，密码同密；本特性仅按契约创建与改密，不做其他写操作
- **邀请码**: 码值、生成参数（前缀/长度/上限/过期）、状态机（available/disabled/finish/expired）、使用者关联表（一人一条，可查历史）
- **角色投影**: 游戏角色库的只读映射（角色标识/名称/种族/职业/等级/头像），服务端按归属校验后展示
- **路由映射**: 旧地址→新路径映射表（文章 ID/页面 ID/分类 ID → 新路径），支持未命中 404
- **积分流水（最小账本）**: 流水类型（M1 仅注册奖励）、数额、备注、时间；余额可由流水重算推导（账本一致性）
- **审计事件**: 命令通道调用、事务邮件发送、安全事件（登录失败/激活异常）的留痕记录

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 抽样 100 个存量真实账号，原凭据登录成功率 100%，全程无重置/无人工介入（M1 验收锚点）
- **SC-002**: 新注册全流程（提交→收邮件→设密完成）可在 5 分钟内走完；完成后同一凭据可立即登录网站与游戏（同密验证通过率 100%）；注册奖励 +2 入账成功率 100%
- **SC-003**: 全部密码变更操作双端一致率 100%，审计中 0 条单边静默成功记录
- **SC-004**: 游戏端不可用期间发起的注册产生 0 个半成品账号（站点侧无孤儿用户）
- **SC-005**: 旧登录/注册/找回地址访问到达新页面比例 100%
- **SC-006**: 命令通道与事务邮件的每次失败均可在审计中查到（失败留痕覆盖率 100%）
- **SC-007**: 用户中心 8 页登录用户全部可达，越权访问他人角色数据 0 成功

## 适用宪法原则（合规映射）

- **原则 I 账号一致性三铁律** → FR-003/FR-004/FR-007/FR-014（注册同步、双写、同密）
- **原则 II 发货必须可靠可见** → FR-023/FR-024（命令通道与邮件失败可见，1,895 单教训的前置防御）
- **原则 III 积分账本可重算** → FR-008（最小账本随 M1 落地，余额=流水推导）
- **原则 IV 兼容与无感迁移** → FR-011/FR-025/FR-026（phpass 无感、旧地址跳转）
- **原则 V 数据边界与生产只读** → FR-022（游戏四库只读姿态、凭据仅 env）
- **原则 VI 安全纵深** → FR-006/FR-013/FR-015/FR-017（复杂度、模糊提示、一次性链接、归属校验）
- **原则 VIII 行为变更必有测试** → SC-001 为自动化验证用例锚点，注册/登录/改密链路必须有测试覆盖

## Assumptions

- **Turnstile 人机验证与登录限速不在 M1**：按计划归 M4（横切），M1 登录/注册暂不接验证码
- **积分账本最小集**（流水+余额，账本可由流水重算）随 M1 落地，服务注册奖励记账与积分页展示；完整积分域（消费/充值/对账任务/全部流水类型）随 M2；订单页 M1 空态
- **物品恢复页**：M1 只读（列表查看），恢复执行属 M2 服务商品链路
- **事务邮件基础能力**（激活/重置邮件发送）随 M1 建立；通知中心与邮件模板体系归 M4
- **服务器状态展示**（在线人数/阵营/uptime）启用归 M4（规格 §6 P1）
- **旧地址映射表内容**：机制 M1 就绪并预置登录类跳转；`?p=`/`?page_id=`/`?cat=` 的全量映射数据随 M3 内容迁移填充
- **邮件域名/发件身份**沿用现有服务器 SMTP 配置，不新增第三方邮件服务
