## 1. 系统概述

**老克塔（lokta.cn）**：魔兽世界 60 年代怀旧服（AzerothCore 引擎）社区门户，"怀旧公益项目"。系统承担四类职责：

1. 社区门户：资讯、教程、论坛、直播入口
2. 游戏数据服务：排行榜/在线玩家/地图/封号记录（iframe 嵌入独立子域）
3. 玩家自助服务：注册开号、角色查询、物品恢复
4. 虚拟商品商城：积分+真实货币双通道，游戏内自动发货

**三条铁律**（贯穿所有模块的设计约束）：
- 站点用户名 = 游戏账号名，注册即同步写入游戏 auth 库（单向站点→游戏）
- 一切涉及密码/账号的变更必须双写（WP 侧 + 游戏 auth 库）
- 商品 SKU `itemsend_{游戏物品ID}` 是商城与游戏世界的映射契约

术语表：积分（站内虚拟货币，源 mycred）· 角色（游戏内人物，GUID 标识）· 发货（SOAP 邮件投递游戏物品）· 服务类商品（改名/转阵营等，无实体物品）· 邀请码（注册凭证）

## 3. 账号体系

### 3.1 注册（P0）
| 功能点 | 现状行为（必须保持） |
|---|---|
| 邀请码 | 必填；4 个码批次（上限 100/50/50/10，已用 32 人次）；可设过期时间；注册成功记占用（用户 ID 追加至码记录 + 用户 meta 记所用码）；状态机 available/disabled/finish/expired；⚠️ 现状缺陷：过期判定懒翻转（仅后台列表加载时执行，未刷新的过期码仍可注册）、users 字段 varchar(20) 易溢出——新系统需注册时实时判过期 + 正经关联表（后台管理能力见 §12 邀请码管理） |

## 5. 商城（P0，营收核心）

### 5.1 商品模型
- 99 个在售商品，14 分类：坐骑31/传家宝28/幻化24/武器14/物理系10/锁甲6/皮甲6/服务5/板甲4/法术系4/饰品3/布甲3/消耗品2/容器1
- 两类商品：**物品类**（SKU=`itemsend_{游戏物品ID}`，发货走 SOAP 邮件）与**服务类**（独立 SKU 作处理器路由键，如 `item-restoration`/`char-change-race`/`char-change-faction`/`char-change-customize`/`char-change-name`，发货走 SOAP 命令处理器；按备份库勘误，原述"服务类无 SKU"有误）
- 无全局属性筛选（未建 pa_ 属性），分类即筛选维度
- 价格区间 10~238（语义=积分）

### 5.2 商品列表 `/shop`
分类筛选 + 价格排序 + 分页 + 全局搜索可达（§10）；商品卡片：图/名/价/分类

### 5.3 商品详情
图集、描述、价格、分类归属；加购；未登录引导登录（物品资料**不再外链 Wowhead**：大陆不可达，#153）

### 5.4 购物车 `/cart`
数量/小计/移除/**积分券抵扣**入口；侧栏"最近浏览"联动；**行内展示下单参数**（角色名/所选恢复物品/目标账号等）供用户复核

### 5.5 结账与发货 `/checkout`（本系统最核心链路）
1. **禁止游客结账**（强制登录；结账页登录提醒开启）
2. **动态角色选择**：下单必须选择名下游戏角色，服务端校验角色归属（防越权下单他人角色）
3. 支付方式：积分支付（主用，余额不足拦截）+ 真实货币网关预留（现状配置过 PayPal 全栈/线下转账/bacs/cheque/cod 顺序）
4. 支付成功链路：**扣积分（写流水）→ SOAP 邮件发货 → 订单状态推进**；失败需重试与人工补发
5. ⚠️ 现状缺陷：发货后订单停留 processing（1,895/1,897）——新系统状态机必须闭环（02 §4）

### 5.6 服务类商品处理器（6+ 种，逐一还原）
改名 · 改阵营 · 改种族 · 改外观(幻化单件/套装) · 装备/物品恢复 · 名字解锁——策略模式：每类一个 SOAP 命令处理器 + 前置校验

> ⚠️ 商品面对齐决策：旧站 WP 从未提供角色转移/角色复制/公会变更三类服务（真机 AC 亦无 `.character transfer/.character clone/.guild change` 原生子命令），**新系统不提供**，处理器/参数矩阵/SOAP 白名单均已收敛。

**下单输入字段矩阵**（按插件源码核实，各商品在商品页采集、购物车行携带、订单行 meta 落库、发货时读取）：

| SKU/处理器 | 下单输入 | 服务端校验 |
|---|---|---|
| itemsend_* 物品类 / 幻化单件 / 幻化套装 / 改种族 / 改阵营 / 外观重置 | 角色选择（名下角色下拉） | 角色归属 |
| item-restoration 装备恢复 | 角色选择 + **可恢复物品单选**：选角色后 REST 异步加载该角色可恢复列表，Wowhead 浮窗展示物品名/图标，单选；与用户中心物品恢复同源 | 支付前校验服务器在线；未选物品不得加购 |
| name-unlock 名字解锁 | 角色选择 + 解锁名（首字母大写规范化） | 名字合法性/占用 |

下单参数随单落订单行 meta（`acore_char_sel`/`acore_restore_item_sel` 等），发货处理器读取执行。

> ⚠️ 决策 D6：现状订单行存在 `acore_msg_dest`（物品类可指定收件角色、寄给他人）能力，**新系统不移植**（用户决策）——物品一律寄给下单所选角色。

### 5.7 订单与售后
- 我的帐户：订单列表/详情（条目、积分金额、状态、发货结果）、支付方式管理（653 paying_customer 存量）
- 后台：订单列表/详情/**手动补发货**、退款、销售报表

## 17. 商品运营 MCP（P1，二期 M6）

**背景**：商品运营当前依赖后台表单逐个添加，效率低；希望通过 Claude Code 等 MCP 客户端直接调用商品接口，完成查询/新增/修改/上下架。

### 17.1 定位与架构口径

- MCP 是**后台能力的对外投影**，不是另一套商品逻辑：所有写入必须经 `services/catalog`（及既有商品 service 层）的同一入口，**禁另写一套 CRUD**；
- 复用既有校验闸门，**不因调用方是 AI 而放松**：SKU↔物品绑定校验（AGENTS 规则 14 `validateSkuBinding`）、服务类处理器注册表命中（规则 16 `handler_key`）、限购口径（规则 17 单次 1 件 + 发货完成释放）、可堆叠物品 `_stack` 后缀强制（规则 18）——违规一律 422 且带 `field`；
- 游戏库不可达即 503（`GameDbError`），不放行未校验商品；
- **不可逆操作不暴露删除**：工具集只提供「下架」，删档须回后台人工处理（见 requirement/01 §3 不做清单）。

### 17.2 工具集（白名单，白名单外一律拒绝）

| 工具 | 作用 | 关键入参 | 备注 |
|---|---|---|---|
| `list_products` | 商品列表/筛选 | 关键词/SKU/分类/类型/上下架态 | 只读；分页返回 |
| `get_product` | 商品详情 | productId | 返回 SKU/价格/库存/发货依据等全字段 |
| `create_product` | 新增商品 | 名称/分类/价格/物品或处理器 | 与后台表单同校验 |
| `update_product` | 修改商品（部分字段） | productId + 变更字段 | SKU 默认只读，改动走高级区且服务端复核 |
| `set_product_status` | 上架 / 下架 | productId + 目标状态 | 下架不影响已成立订单的发货 |
| `list_categories` | 分类字典 | — | 只读，供新增商品时选分类 |

> 工具参数与返回统一走 Zod 校验（边界不信任外部输入）；工具描述文案由服务端生成，保证与实际校验一致。
> **落位**：服务域 `services/mcp/`（工具注册表 + 令牌鉴权），商品读写经 `services/catalog` 复用既有入口；路由 `src/app/api/mcp/route.ts`。

### 17.3 鉴权与治理

- **鉴权独立于站点会话**：长期访问令牌（Bearer），令牌本身按「只写不读」处理（AGENTS 规则 12 `secret` 模式）存 `system_config` 的 `mcp` 组，仅存哈希，不存明文；
- 令牌绑定管理员身份 + 作用域（可限定只读 / 可写）+ 有效期；后台可签发、吊销、查用量；
- 每次调用记审计（`audit_log`），**只记 id 与结果**（工具名/目标 id/成败/耗时），不记令牌、不记请求体全文；
- **令牌级限速**：每令牌 QPS 与每日调用上限，超限返回 429（复用既有 `hitRateLimit` 原语与 `security` 组后台可调口径）；
- 工具调用**不得执行任意 SQL / 通用表写入 / 文件系统操作**。

### 17.4 传输形态（**已定：Streamable HTTP**）

- **传输 = MCP Streamable HTTP**，单端点 `POST /api/mcp`（与现有 Next.js 部署同域），零额外运维、便于令牌鉴权与限速；
- 不做 stdio 本地桥接（仅当某个客户端不支持 HTTP 传输时再评估，属例外路径）；
- 协议版本与能力协商按 MCP 官方 Streamable HTTP 规范实现，工具清单由服务端注册表生成（客户端 `tools/list` 拿到即当前白名单）。

### 17.5 错误口径

沿用站内 `apiError` 约定：校验失败 422 `VALIDATION_FAILED`（带 `field`）· SKU 不合规 422（带 `field: sku|gameItemId`）· 游戏库不可达 503 · 令牌无效 401 · 越权/超限速 403/429。

## 18. 内容聚合与信息流（P1，二期 M7）

**背景**：现有资讯页只有站内原创文章；希望接入外部游戏资讯与视频源（B站/抖音等），让资讯页成为**信息流**，提升内容丰富度并带来攻略类长尾内容。

### 18.1 数据模型（对齐 aitech-hub 口径，三表）

> 参照 aitech-hub 的成熟采集模型（`CrawlSource` 源台账 / `CrawlSnapshot` 抓取快照 / `SocialAccount` 博主台账 + 内容表 `Telegram`），本项目对应：

| 表 | 作用 | 关键字段 |
|---|---|---|
| `feed_source`（源台账） | 每个采集源的运行契约 | `source_key`（唯一）· `name` · `type`（rss/api/web/social-video）· `enabled` · `interval_min`（≥30）· `daily_max_requests` · `consecutive_fails` · `last_run_at` · `next_run_at` · `status`（ok/error/paused）· `failed_reason`（人话）· `config`（JSON，源私有配置，敏感项加密） |
| `feed_account`（博主台账） | 定向跟更的账号/频道（B站 mid、抖音 sec_uid 等） | `platform` · `external_uid`（**联合唯一**）· `display_name` · `last_post_at`（**增量地板**：下次只取更新的）· `enabled` |
| `feed_item`（内容） | 抓回来的条目 | `source_id` · `external_id` · `content_hash`（**sha1(title+url) 唯一去重键**，aitech-hub 同款）· `title` · `summary` · `cover_url` · `source_url`（原文外链）· `author` · `published_at` · `kind`（资讯/攻略/视频）· `media_type` · `status`（visible/hidden/archived）· `fetched_at` |
| `feed_snapshot`（抓取快照） | 取数原文档案，供回溯与排障 | `source_id` · `sha1` · `size_bytes` · `parse_status` · `storage_key`（可选，COS 归档） |

> 与 `Article` **不合并**：`Article` 是站内编辑内容，走正文 Markdown 渲染、SEO sitemap、阅读计数与评论；聚合条目是**外链引用型内容**（无正文，或仅摘要），两者生命周期、渲染与 SEO 口径都不同，合并会让外链内容污染站内正文链路。
> 唯一键 = `content_hash`（sha1(title+url)），辅以 `(source_id, external_id)` 二级键。

### 18.2 采集管道（对齐 aitech-hub 调度口径）

- **调度**：**DB 驱动 tick**——cron 脚本（`scripts/cron/fetch-feeds.mjs`，与既有备份/对账/补发脚本同目录同形态）每 N 分钟扫 `next_run_at` 到期源，逐源抓取；每源间隔由源自身 `interval_min` 表达（**≥30 分钟**，博主账号 ≥120 分钟），**不用 cron 表达式逐源硬编码**；
- **并发**：全局并发上限 2（同 aitech-hub 默认），单源失败不阻塞其他源；
- **幂等与去重**：入库按 `content_hash` upsert；已存在条目仅更新易变字段（标题/封面/统计），不产生新行；`feed_account.last_post_at` 作增量地板，避免重复翻页；
- **失败处理**：连续失败 ≥3 次 → 源 `status=error` + `failed_reason` 写**人话原因**（不是堆栈）；**429 限流只顺延不记失败**（与 aitech-hub 同款，避免把限流误判成源坏了）；网络错误按有限次重试；
- **告警**：连续失败进飞书告警通道（复用 AGENTS 规则 19 既有 webhook），**失败必须可见**，禁止静默；
- **抓取日志**：每次抓取落 `feed_snapshot` + 运行台账（时间/条数/失败原因），后台可见（§12 内容源管理）。

### 18.3 采集源类型分层（**决定工作量与合规风险的关键**）

| 类型 | 手段 | 合规风险 | 举例 |
|---|---|---|---|
| `rss` | `fetch` + XML 解析 | 低 | 官方公告 RSS、第三方 RSS 桥 |
| `api` | 公开 JSON API | 低 | 站点公开榜单/接口 |
| `web` | 静态 HTML + cheerio 解析 | 中（须看 robots） | 公开榜单页、静态页 |
| `social-video` | **短视频平台网关 sidecar**（**已定：仿 aitech-hub**） | 中高（见下） | B站 / 抖音 |

> **短视频源口径（已定）**：仿 aitech-hub 的做法——B站/抖音经**独立 Python 网关 sidecar** 采集（a_bogus/wbi 签名 + Cookie 池 + 出口代理轮换），本项目侧只做 HTTP 契约调用（Zod 契约镜像 + 双侧 fixture 对拍，同 aitech-hub 口径）。
> **边界与 aitech-hub 一致：只做基本信息索引与转发，不做存储**——只落「标题 / 摘要 / 封面 URL / 原文外链 / 发布时间 / 作者」；**播放地址过境即焚、不落库**，视频本体不转存、不二次分发。
> 代价与前置：① 生产栈要新增一个 Python 常驻服务（采集网关，**不是业务微服务**，与「不引入微服务」不冲突，但须在 dev/test/prod 三套 compose 同步登记，且 prod 文件头「刻意排除清单」不适用——它是生产必需组件）；② 签名算法需随平台变更持续跟进（平台改签名即须跟进）；③ Cookie 池与代理凭据按 `system_config` 加密存（禁入 env / 禁入文档），轮换与失效有后台可见状态；
> 合规红线不变：仍**不养号、不批量注册、不绕付费墙、不破验证码**；只采平台公开可见内容。

### 18.4 合规边界（硬约束）

- **只采公开元数据**（标题/摘要/封面 URL/发布时间/作者/原文链接），**不转存视频本体、不二次分发**，前台播放走原站外链（requirement/01 §3 已列入不做清单）；**播放地址只过境即焚、不落库**（aitech-hub 同款版权红线）；
- **短视频源走签名网关**（§18.3 已定）：只调用平台**公开可见内容**的接口，不养号、不批量注册、不绕付费墙、不破验证码、不破反爬；robots 明确禁止的源不采；
- **robots 检查须真实实现**（aitech-hub 只写在文档、代码未落地；本项目要立规矩则须落地）；
- **UA 声明**：统一 `acore-portal-crawler/1.0 (+https://lokta.cn)`，可识别、可联系；
- 频率控制：每源 `interval_min` + `daily_max_requests` + 全局并发上限，避免对源站造成压力；
- **封面图热链 + 失败回退占位图**（**已定**）：不转存 COS——零存储与带宽成本，代价是源站防盗链时可能取不到图（回退占位图，不做图片代理）；
- 聚合条目**不进站内 sitemap**（避免低质外链影响 SEO 权重），仅在信息流页出现。

### 18.5 前台信息流

- 资讯页由「站内文章列表」升级为「信息流」：**聚合条目 + 站内文章**混排，按发布时间倒序，支持按来源/类型筛选；
- 每条聚合条目**必须标注来源与「站外」标识**，点击跳原文（新窗口），不伪装成本站内容；
- 保留站内文章的原有归档路径（`/news` / `/guides` / `/announcements`）与单篇详情页不受影响。

### 18.6 后台源管理（§12 内容源管理）

- **采集源台账**：新增/编辑/启停源（来源标识、类型、入口地址、抓取间隔、每日请求上限、失败阈值），列表显示状态 / 上次运行 / 下次运行 / 连续失败次数；
- **博主台账**：新增/停用跟更账号（B站 mid、抖音 sec_uid 等），显示最近发布时间与增量地板；
- **运行台账**：抓取运行记录（时间/源/条数/失败原因/耗时），失败原因人话化；
- **条目治理**：聚合条目下架（`status=hidden`）与批量下架、来源黑名单（不再抓某源）。

**落位**：服务域 `services/feed/`（条目模型 + 采集管道 + 源管理），抓取调度脚本 `scripts/cron/fetch-feeds.mjs`；新增业务表 `feed_source` / `feed_account` / `feed_item` / `feed_snapshot` 走 Prisma 迁移。

## 19. 站内搜索（P1，二期 M8）

**背景**：M7 引入大量外部聚合条目后，用户需要能检索视频、攻略、帖子，而不只是站内文章。

> **交付分两段（计划评审定）**：**M8-a** = 词项层 + 分组结果页 + agent 检索工具 + 资讯/帖子/商品/静态页·FAQ 四类内容，**零依赖可先行**；**M8-b** = 接入 M7 的 `feed_item` 第五类及其向量化，待 M7 条目模型落地。语义层（embedding）随 M8-a 先行接入四类内容，M8-b 补第五类。

### 19.1 覆盖范围（跨类型检索）

| 类型 | 数据源 | 命中面 |
|---|---|---|
| 资讯/攻略（站内） | `Article` | 标题 + 摘要 + 正文 |
| 聚合条目 | `feed_item` | 标题 + 摘要 + 类型 |
| 帖子 | `ForumThread` + `ForumPost` | 主题标题 + 回复正文 |
| 商品 | `Product` | 商品名 + 描述 + SKU |
| 静态页/FAQ | `ContentPage` / `ProductFaq` | 标题/问题 + 正文 |

### 19.2 结果页

- 路径 `/search?q=`，**按类型分组**展示，每组内按相关度/时间排序，组内显示摘要片段与命中高亮；
- 无结果时给出替代路径（分类归档 / 提问求助入口），不出现空白页；
- 支持按类型过滤与分页。
- **两种检索入口共用同一检索 service**：① 经典结果页（一次查询 → 分组列表）；② **agent 问答式检索**（多轮改写 + 工具协作，见 §19.4），后者是「更精准」的主形态，前者是兜底与快速通道。

### 19.3 与既有搜索并存

- 既有归档内搜索（`/news?q=` 等，标题 LIKE）**保留不改**，作为「在归档内筛选」的轻量路径；
- 侧栏全局搜索框（§2.1 既有组件）指向 `/search`，输入回车提交。

### 19.4 检索架构（**已定：deepagents 编排 + 混合检索**）

参照 aitech-hub 的成熟形态（`deepagents` npm 包 + 混合检索 + 统一检索 service），移植口径：

- **编排层 = deepagents**（LangChain 官方 deep agents 的 TS 包）：检索不再是「一次查询返回结果」，而是 agent 自主多步——列计划 → 检索 → 读正文 → 必要时改写查询再检 → 汇总作答，精度增益来自**多轮改写与工具协作**；
- **工具面**（与 aitech-hub 同构）：`search_site`（跨类型检索）· `read_document`（展开某条正文）· `get_time`（锚定「今天/最近」等相对时间）· `ask_user`（关键信息缺失时结构化提问，缺此会卡死）；**只读红线**——除反馈类工具外 agent 不写入任何数据、无站外网络、无代码执行；
- **deepagents 最小配置用（硬约束）**：
  ① **工具面只读且收敛**——只注册上述 4 个工具；**禁用文件系统 / Shell / 沙箱后端**（backend 固定为内存态，禁止注册 `LocalShellBackend` / `LangSmithSandbox`），杜绝「agent 能读写服务器文件」的攻击面；
  ② **步数与预算闸**——单次问答最大工具迭代步数（默认 8）+ 单次 token 上限 + 日配额（与 §20.3 同一套配额），超限即中断并如实告知；
  ③ **不接 LangGraph checkpointer**——官方 saver 只有 SQLite/Postgres（**无 MySQL saver**），接了就得引 PG；会话历史自存 MySQL 表逐轮注入（§20.1）；
  ④ **中间件只挂必要项**——规划（todo）+ 工具调用纠错 + 悬空 tool_call 修复（aitech-hub 生产实践：护栏中间件仍须自写，deepagents 不是「开箱即用」）；不启用技能库 / 子代理 / 记忆中间件；
- **检索底座 = 混合检索**（两榜 RRF 融合，k=60）：
  - 词项层：MySQL **ngram 全文索引**（`FULLTEXT ... WITH PARSER ngram`，MySQL 8.4 内置）+ 字段加权（标题 > 摘要 > 正文）；
  - 语义层：query 向量化 → 向量召回（存储选型见 §19.5）；
  - 融合：两榜 RRF（k=60）合并，同分时词法证据优先；**语义层不可用即整体降级**（结果退化为单榜，不报错）。
- **统一检索 service**（aitech-hub 核心纪律）：**给人搜 = 给 agent 搜 = 给 MCP 搜**同源——同一个 `services/search` 检索 service 同时供 `/search` 结果页、agent 工具、MCP「搜索」工具，避免三处口径漂移；
- **会话持久化**：见上方 ③（会话历史自存 MySQL，与 M9 对话历史表合并为一张，见 §20.1）。

**Agent 框架选型评估（已定 deepagents）**

| 候选 | 契合度 | 成本 / 风险 | 结论 |
|---|---|---|---|
| **deepagents**（LangChain 官方 TS 包 ^1.14.2） | 规划中间件 + 工具循环 + 中间件链开箱；`model` 接受 LangChain 模型实例 ⇒ **anthropic / openai 兼容双协议天然可接**；`checkpointer` 可选 | 本体依赖极轻（fast-glob/micromatch/yaml/zod），但拉入 `@langchain/core` + `langgraph` + `langchain`（安装盘约 44M，服务端运行不进浏览器包）；1.x 迭代快、**版本 churn 风险**；内置文件/Shell/沙箱工具**须显式关掉** | **采纳**——与 aitech-hub 同款，团队已有实测踩坑经验（todo 需显式挂、护栏中间件要自写） |
| LangGraph 原生 StateGraph | 只做「多步工具循环 + 只读工具 + 流式」够用，但要自己拼图与中间件（~200-300 行） | 少一层封装与 3M 依赖 | **退路**——若 deepagents 迭代带来破坏性变更，回落自建图 |
| Vercel AI SDK | 前端流式 UI 最省 | agent 编排弱（需自写 loop），与 LangChain 模型层割裂 | 不推荐（我们重心在服务端检索精度） |
| Mastra | 功能全、TS-first | 生态小、依赖重、模型适配要额外写 | 不推荐 |
| 自写 tool-calling loop | 最轻 | **双协议 tool-call 形态差异（Anthropic `tool_use` vs OpenAI `tool_calls`）需自处理**，省下的依赖不抵自维护成本 | 不推荐 |

> **依赖兼容性已实测核对**（非推测）：`@langchain/core@1.2.16` 依赖 `zod ^3.25.76 || ^4` ⇒ **本仓 zod 3.25.76 直接可用，无需全仓 zod 3→4 迁移**；deepagents 走 `zod/v4` 子路径，而 zod 3.25.76 自带该子路径 ⇒ 无双版本割裂；Node 要求 ≥20，本仓 Docker 为 node:22 ✓。

### 19.5 向量存储选型（**已定：MySQL 存向量 + 应用层召回，不引入 pgvector**）

acore-portal 是 **MySQL 8.4**（无原生 VECTOR 类型、无 pgvector），aitech-hub 的 pgvector 方案不可直接搬：

| 候选 | 结论 |
|---|---|
| **A（采纳）MySQL 存 embedding（BLOB/float32）+ 进程内向量索引 + 应用层暴力余弦** | 零新增组件。站内可检索语料量级 ≈ 1e4（教程攻略数百 + 聚合条目数千 + 帖子数千），1e4 × 1024 维 × 4B ≈ 40MB，进程内加载 + 暴力点积毫秒级，够用 |
| B 加 PG + pgvector sidecar（aitech-hub 同款） | 新增常驻服务 + 双库同步 + compose 与运维面变更，违背「单体优先 / 不引入新组件」；条目数增长后仍可作为升级路径 |
| C 外部向量库（Qdrant/Meilisearch） | 更重，且与 A 的收益差在当前量级下不显著 |
| D 纯关键词 + LLM 重排（不做向量） | 最省，但语义召回弱，且无法满足「更精准」的诉求 |

- **Prisma 不支持 vector 类型** ⇒ 向量列用 `Bytes`（或 JSON）+ raw SQL 存取（aitech-hub 同样以 `Unsupported("vector(1024)")` + raw SQL 绕过）；
- **embedding 模型走 openai 兼容协议**（Anthropic 协议无 embedding 端点，见 §20.3），供应商后台自选；
- **降级与重建**：向量层失败 ⇒ 检索退化为词项层（不报错）；进程内索引随内容变更增量更新，进程重启时从 MySQL 重建（派生数据，丢了可重算，不影响真相源）；
- **升级阈值**：语料超过 **5 万条** 或单次召回延迟不达标时，重评 B 方案（PG + pgvector sidecar）。

### 19.6 限速与统计

- 搜索属高消耗入口：**按 IP 限速**（复用 `security` 组既有限速口径，阈值后台可调），未登录用户更严；
- 搜索词进统计看板「搜索词」维度（沿用 §12 统计看板口径），用于判断站内内容缺口；
- agent 多步检索**放大成本**：单次问答的模型调用数与 token 计入日配额（与 §20.3 的 `dailyMax` 同一套配额体系）。

**落位**：服务域 `services/search/`（跨类型检索 + 分组结果），数据面跨 `content` / `forum` / `catalog` / `feed` 四域——按 AGENTS「域间横向 import 由 eslint-plugin-boundaries 拦截」口径，须在 `eslint.config.mjs` 的 `ORCHESTRATION_EDGES` 登记编排边，或由 `services/search` 读取各域的只读列表函数而非直连其表。

## 20. AI 助手（P2，二期 M9）

**背景**：用户对「怎么下载客户端 / 怎么登录 / 补丁去哪打」等常见问题反复咨询，希望站点提供智能问答。

### 20.1 入口

- 页头/页脚固定「AI 助手」入口 → 独立页 `/assistant`（对话式），另有**悬浮按钮**形态（决策点：悬浮按钮可能遮挡内容与移动端操作，倾向独立页 + 移动端底部条）；
- 对话历史**服务端存储**（按用户），可查看与清空；游客不提供历史（无账号即无法关联）。
- **持久化方式**：不接 LangGraph checkpointer（官方无 MySQL saver，见 §19.4），会话消息自存 MySQL（`assistant_session` + `assistant_message`），逐轮注入 agent 上下文；历史按留存期清理（后台可配）。

### 20.2 知识源（检索面）

- 站内教程/指南类 `Article`（客户端下载、补丁、登录器）、静态页 `ContentPage`（项目简介/使用教程/协议）、商品 `ProductFaq`、论坛精选帖（`ForumThread` 标记为精选）；
- **检索走站内搜索面**（M8 能力）⇒ M9 依赖 **M8** 的检索面（**不另建一套向量库检索**）；知识源为站内教程/静态页/商品 FAQ/论坛精选帖，**不含 `feed_item`**，故 **M7 不是 M9 的必需前置**（M7 落地后仅让检索面多一类可命中来源）；
- 未被检索覆盖的问题**明确拒答**，不编造。

### 20.3 LLM 通道配置

- **供应商不绑定**：通道全部由后台自定义配置，**同时支持两种协议**——
  - `anthropic`：走 Anthropic 协议（`/v1/messages` 语义），对接 Claude 等原生协议服务；
  - `openai`：**OpenAI 兼容协议**（`/v1/chat/completions` 语义），对接 DeepSeek / 智谱 / Qwen / 各类兼容网关。
- 配置项（`system_config` 新增 `llm` 组，按「模型条目 + 角色绑定」两层组织）：

  | 字段 | 说明 |
  |---|---|
  | `protocol` | `anthropic` / `openai`（Zod 校验，非法值拒绝） |
  | `baseUrl` | 自定义服务地址（OpenAI 兼容网关常需改 base） |
  | `modelId` | 模型名（供应商自定义名不做任何假设） |
  | `apiKey` | **只写不读**（AGENTS 规则 12 `secret` 模式）：后台不回显，留空 = 保持现值 |
  | `systemPrompt` | 系统提示词（助手角色与检索角色可分别配置） |
  | `timeoutSec` / `dailyMax` | 超时与日配额（每模型 + 每角色两层） |
  | `enabled` | 单模型启停 |

- **角色绑定**：同一模型可绑多个角色（`assistant` 对话助手 / `search` 检索编排 / `embedding` 向量），按角色选主力模型；主力不可用时降级（§20.3 降级口径）。
- **embedding 仅 openai 协议**——Anthropic 协议无 embedding 端点，故向量模型必须配 `openai` 协议（参照 aitech-hub 同口径）。
- **多协议同构**：上层（对话编排、检索 agent、embedding、摘要）只认「角色」，不认协议；协议差异收口在通道客户端内（`ChatAnthropic` / `ChatOpenAI` 两条实现，配置层零分支）。
- 通道不可用 / 超时 / 配额耗尽 ⇒ **降级**到站内搜索结果 + FAQ 列表（不返回错误页）。

### 20.4 回答规范

- 回答**必须附来源链接**（引用的教程/FAQ/帖子链接），无来源的回答不予输出；
- 检索无命中时明说「没找到相关说明」并给出建议路径（提问求助 / 论坛板块），**禁止编造步骤**；
- 安装/下载类回答**不得臆造下载链接**——链接一律来自站内内容源。

### 20.5 成本与隐私

- **日配额**（每用户 + 全站双层），超限提示并降级；
- **问题脱敏**：不上送用户个人信息（账号/邮箱/角色名），命中站内检索所需字段先本地过滤；
- 用户提问与回答留痕可审计（审计只记 id 与用量，不记提问全文的敏感部分），后台可关停助手总开关；
- 站点自有内容送入模型前可做**内容授权标注**（站内原创内容标注来源，聚合外链内容只送摘要不送全文，降低第三方内容外送风险）。

**落位**：服务域 `services/assistant/`（对话编排 + 检索 + 降级），LLM 通道配置读 `lib/config.ts` 的 `llm` 组（配置新增时同步在 `src/constants/` 补字段常量）；检索面复用 M8 的 `services/search`。
> 二期（2026-11 起）：M6 约 1 周 · M7 约 3-4 周（含 Python 网关 sidecar 移植与三套 compose 接线）· M8 约 1-2 周 · M9 约 2 周。
