# 商城分类树修复手册(shop-category-tree-fix)

> 一次性数据修复:把商城商品从「压成单分类 + 分类表有重复行」修回
> 「单分类 + 父子聚合」的商品分类树,并重建分类树与排序。
> 配套脚本:`scripts/ops/fix-shop-category-tree.sql`(修复)、
> `scripts/ops/fix-shop-category-tree.rollback.sql`(回滚)。

## 1. 背景:为什么点了筛选全是空的

旧 WordPress 站用 WooCommerce 的 `product_cat` 分类归档,商品可以同时挂多个分类,
前台按父子关系聚合展示。迁移到新站时分类信息被压扁,产生三个**互相独立**的成因
(均在生产库实勘确认,不是推测):

| # | 成因 | 表现 | 实测影响 |
|---|---|---|---|
| A | 迁移脚本用 `MIN(c.id)` 给商品取分类 | 一件挂多个 WP 分类的商品只保留 id 最小的那个,**而父分类 id 往往更小** | 14 件武器各挂「传家宝 + 武器 + 物理系/法术系」,全部落在「武器」⇒「物理系」「法术系」两个子类恒为 0 件 |
| B | 迁移脚本插分类时不去重 | WP 侧部分中文分类的 slug 是 `%xx` 百分号编码,同名分类被插了两遍,带 `%xx` 的那行 0 商品 | `product_category` 多出 9 行重复分类,且全部 `sort = 0` ⇒ 前台 filesort 顺序随机,**用户点到的第一个同名项恰好是空的那行** |
| C | 幻化商品在 WP 存量里本来就是草稿 | 24 件幻化是 `draft` | 旧站同样筛不出来 ⇒ 正确行为是「计数 0 即不出现」,而不是「显示出来再报空」 |

三者的修复方向不同:**A 改商品归属、B 删重复行、C 不动**(用户裁决:幻化保持草稿不上架)。

## 2. 修复口径

- **商品归属取最深的 WP `product_cat` term**(同深取 `term_id` 最小 ⇒ 结果确定);
  父分类不再直接挂商品,前台按父子聚合展示(单分类 + 父子聚合)。
- **只改归属,不改 `status` / `listed`** ⇒ 幻化仍是草稿,商品可见性零变化。
- **分类 slug 一律不动** ⇒ 旧书签 `?category=<slug>` 继续可用。
- **分类树按 WP 的 `parent` 关系重建**,`sort` 改成「同父内序号」的全局前序序
  (`sort = parent.sort * 100 + 同父序号`,根分类为 `同父序号 * 100`;限深 ≤ 4,Int 范围内不溢出)。
- **幂等**:重跑零变更(删过的行已不存在;归属已是目标值;`sort` 已是目标值)。

## 3. 执行步骤

### 3.1 前置

1. `wp_legacy` 与业务库同实例(生产 WP dump 已导入同实例)。
2. 先按 `docs/ops/backup-restore.md` 备份业务库(`product` / `product_category` 两表)。

### 3.2 预检(只读)

```bash
mysql -h <host> -u <user> -p <业务库名> < scripts/ops/fix-shop-category-tree.sql
```

脚本开头 `SET @apply_fix := 0` ⇒ 只跑 ① 段只读预检(仅建一个空的备份表,不动业务数据)。
核对下列输出:

| 段 | 期望 |
|---|---|
| ①-2 同名重复分类 | 9 行(全是 `%xx` 编码且 0 商品的重复行) |
| ①-3 未解码 slug | 9 行 |
| ①-4 待改归属商品 | 14 行(全部是武器,应拆成 物理系 10 / 法术系 4) |
| ①-5 目标 vs 当前 | 目标 15 分类行 / 0 重复名 / 0 未解码 slug / 61 已上架 / 39 草稿;当前 24 / 9 / 9 / 61 / 39 |

若 ①-4 的行数或分布与上表不符,**中止**并重查存量数据。

### 3.3 执行修复

把脚本开头的 `SET @apply_fix := 0` 改成 `1`,重跑同一命令:

```bash
mysql -h <host> -u <user> -p <业务库名> < scripts/ops/fix-shop-category-tree.sql
```

脚本四段:① 只读预检 → ② 快照落 `ops_shop_category_bak` → ③ 修复(商品归位 / 删重复行 /
重建 `parent_id` / 重排 `sort`)→ ④ 后置校验。

### 3.4 后置校验

④-2 段应输出:

```
已上架总数 61 | 草稿总数 39 | 分类行数 15 | 重复名数 0 | 未解码slug数 0 | 悬空归属数 0
```

分类明细(④-1)应为:

| 分类 | `sort` | 已上架 |
|---|---|---|
| 坐骑 | 100 | 17 |
| 消耗品 | 200 | 2 |
| 服务 | 300 | 5 |
| 传家宝 | 400 | 0(父分类,按子树聚合) |
| 幻化 | 500 | 0(草稿,不上架) |
| 容器 | 600 | 1 |
| └ 武器 | 40001 | 0 |
| └ 布甲 / 板甲 / 锁甲 / 饰品 / 皮甲 | 40002–40006 | 3 / 4 / 6 / 3 / 6 |
| └ └ 物理系 / 法术系 | 4000101 / 4000102 | 10 / 4 |

传家宝子树合计 = 3+4+6+3+6+10+4 = **36**,与修复前一致 ⇒ 商品零丢失。

### 3.5 快照保留

`ops_shop_category_bak` 保留 **3–7 天**后再清理(回滚窗口)。

## 4. 回滚

```bash
# 先只读预检
mysql -h <host> -u <user> -p <业务库名> < scripts/ops/fix-shop-category-tree.rollback.sql
# 核对后把 @apply_rollback 改成 1 重跑
```

回滚口径:补回被删的 9 行重复分类(原 id 原样恢复)→ 还原存活分类行的
`name` / `slug` / `parent_id` / `sort` → 还原商品的 `category_id`。
回滚后 ③-2 / ③-3 两段应**无差异行**,③-1 的「缺失行数」应为 0。

**注意**:回滚后 `ops_shop_category_bak` 保留为审计痕迹。若回滚后**再次**执行修复脚本,
须先 `TRUNCATE TABLE ops_shop_category_bak`——否则 `INSERT IGNORE` 不会刷新快照,
二次回滚会还原到**第一次修复前**的状态而非当前状态。

## 5. 风险与兜底

| 风险 | 兜底 |
|---|---|
| 脚本误删有商品的分类 | ③-2 的删除条件含「自身 0 商品 且 无子分类引用」两道闸;预检段先打印全部将删行 |
| 幻化 24 件被误发布 | 脚本**只改归属不改 `status`**;④-2 断言已上架恒为 61 |
| 旧书签 `?category=<slug>` 失效 | slug 一律不动 |
| 误操作生产库 | `ops_shop_category_bak` 快照 + 配套 rollback.sql;先跑只读预检 |
| 商品直达链接/详情页面包屑受影响 | 商品页按分类名展示,不依赖分类层级;修复后抽查 `/shop` 与商品详情页 |

## 6. 关联:防重演

本脚本是**一次性修复**;迁移链的源头缺陷(`scripts/migrate/shop-import.sql` 的分类去重、
slug 解码、非零 `sort`、最深 term 取值)另行修正,并在 `scripts/migrate/reconcile.mjs`
补分类覆盖断言,防止"静默丢分类"再次通过迁移链。详见开发计划对应条目。
