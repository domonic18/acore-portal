### M6 运营提效: 商品运营 MCP

- 目标: 把后台商品能力以 MCP 协议对外暴露，供 Claude Code 等客户端调用——查询/新增/修改/上下架，取代逐个填表单
- 验收标准（可执行）:
  1. **令牌鉴权生效**——无令牌/错令牌调 `POST /api/mcp` 返回 401；有效令牌可 `tools/list` 拿到 6 个白名单工具（§17.2）
  2. **白名单工具全量可用**——`list_products`/`get_product`/`create_product`/`update_product`/`set_product_status`/`list_categories` 逐个调用成功，白名单外工具名返回拒绝
  3. **每次调用可审计**——`audit_log` 落一行，只含工具名/目标 id/成败/耗时，**不含令牌与请求体全文**
  4. **与后台表单同校验**——同一违规输入（MCP 与后台表单各一次）均返 422 且 `field` 一致（`sku`/`gameItemId`）
  5. **限速生效**——超令牌级 QPS/日配额返回 429
- 预估工作量: 1 周
- 状态: **未开始** — 规格 §17；**传输已定：MCP Streamable HTTP**（`POST /api/mcp`，零额外运维、不做 stdio 桥接）；**鉴权口径已定**（§17.3：令牌只写不读、仅存哈希，绑定管理员身份+作用域（只读/可写）+有效期，审计只记 id，令牌级限速复用 `hitRateLimit`）
- 依赖: 无（可先行）
- **后续返工（登记在此避免漏项）**：M8 交付统一检索 service 后，须回 M6 补一个 `search_site` 工具（规格 §19.4「给人搜=给 agent 搜=给 MCP 搜」同源），否则 MCP 与站内检索两套口径漂移

### M7 内容聚合: 资讯与视频信息流

- 目标: 外部游戏资讯与视频源采集管道 + 聚合条目模型 + 资讯页升级为信息流 + 后台源管理
- **分两段交付（2026-11-09 决策：先 RSS/公开 API 源出成果，短视频网关后置）**:
  - **M7-a 采集骨架 + 信息流**——源台账 / 博主台账 / 抓取快照 / sha1 去重 / DB 驱动 tick 调度 / 连败降级 / robots 检查 / 前台信息流页 / 后台源管理；**源范围限 RSS、公开 JSON API、静态 HTML**（无需签名、无需 Cookie 池、无需代理，合规与运维风险最低）
  - **M7-b 短视频网关**——独立 Python sidecar 做平台接口签名（a_bogus/wbi）+ Cookie 池 + 出口代理轮换；TS 侧只做 HTTP 契约调用（Zod 契约镜像 + 双侧 fixture 对拍）+ 三套 compose 接线；**排在 M7-a 出成果之后**
- 验收标准（可执行，M7-a）:
  1. **至少 2 个源稳定产出条目**——连续 3 轮调度均有新条目入库（失败重试与退避生效，不静默）
  2. **去重零重复**——同一 URL 重复采集不产生第二条记录（sha1 去重键断言）
  3. **前台信息流可按来源/类型筛选**——筛选结果与条目来源一致，每条带来源与「站外」标识
  4. **抓取失败有重试与告警**——源连续失败 ≥3 次置 `error` 且落飞书告警（复用规则 19 通道）
  5. **robots 检查真实生效**——被 robots 禁止的源不被采集（有单测断言，非仅文档声明）
  6. **不落播放地址/不转存本体**——`feed_item` 无播放地址字段，封面为热链 URL
- 验收标准（可执行，M7-b）:
  1. **短视频条目可稳定入库**——连续 3 轮调度均有新条目，且网关与 TS 侧契约双侧 fixture 对拍通过
  2. **播放地址过境即焚**——`feed_item` 与日志中均无播放地址字段，前台只存外链

- 状态: **未开始** — 规格 §18；**实现口径对齐 aitech-hub**（源台账 + 博主台账 + 抓取快照 + sha1 去重键 + DB 驱动 tick 调度 + 连败降级 + 人话失败原因 + robots 检查落地）；**短视频源已定仿 aitech-hub**（独立 Python 网关 sidecar 做平台接口签名 + Cookie 池 + 代理轮换，只做基本信息索引与转发、不做存储；生产栈须新增该 sidecar 服务并同步 dev/test/prod 三套 compose）；**封面已定热链 + 占位回退，不存 COS**；**分段决策已定（2026-11-09）：M7-a 先做 RSS/公开 API 源，M7-b 短视频网关后置**

### M9 AI 助手: 站内智能问答

- 目标: 对话入口（/assistant）+ 站内知识检索 + LLM 通道配置 + 降级与配额，回答安装/下载等常见问题
- 验收标准（可执行）:
  1. **回答必附来源链接**——每个回答含 ≥1 条站内来源链接且可点开
  2. **检索不到时明说而非编造**——无命中时回答中不出现未在语料中出现的断言
  3. **通道故障自动降级**——LLM 通道不可用时降级到站内搜索/FAQ 并提示，不 500
  4. **日配额生效**——超配额后拒绝新会话并提示，既有会话不受影响
  5. **双协议可配**——anthropic 协议与 openai 兼容协议各配一条通道，均可完成一次问答；密钥不读、只写
- 预估工作量: 2 周
- 状态: **未开始** — 规格 §20；**LLM 通道已定：后台自定义，协议双支持**（anthropic 原生协议 + openai 兼容协议），按「模型条目 + 角色绑定」两层组织，密钥只写不读；embedding 角色仅 openai 协议；待用户确认：首批 LLM/embedding 供应商与密钥（requirement/01 §6，开发时提供）
- 依赖: **M8（检索面）**——知识源为站内教程 `Article` / 静态页 `ContentPage` / 商品 `ProductFaq` / 论坛精选帖（规格 §20.2），**不含聚合条目** ⇒ **M7 不是 M9 的必需前置**，M8-a 交付即可开工
- **风险**：embedding 供应商可达性与成本（国内可达性未验）；agent 多步检索放大 token 消耗（计入日配额）；LLM 通道配置错误导致降级频发

### 优先级排序理由（四维对照）

| 里程碑 | 用户价值 | 依赖就绪度 | 外部风险 | 工作量 | 建议序位 |
|---|---|---|---|---|---|
| M6 | 高（运营直接受益，免手工逐个填商品） | 无依赖 | 低（协议、工具面、鉴权口径均已定） | 1 周 | 1 |
| M8-a | 中高（全站内容首次可检索，是 M9 与 MCP 搜索的共同底座） | 无依赖 | 中（deepagents 版本 churn，已备退路） | 1-1.5 周 | 2 |
| M7-a | 中高（内容丰富度与留存） | 无依赖 | 低（RSS / 公开 JSON API / 静态 HTML，无需签名与 Cookie 池） | 1-1.5 周 | 3（并行） |
| M7-b | 中高（补上短视频这一最大流量品类） | 依赖 M7-a | **高**（平台签名算法变更、须新增常驻 sidecar 与三套 compose 接线） | 2-3 周 | 4（后置） |
| M9 | 中（问答属锦上添花） | 依赖 M8-a + 外部密钥 | 中（embedding 可达性与成本未验） | 2 周 | 5 |

排序原则：

1. **先做「不依赖别人、且天天踩」的**——M6 替掉运营手工填商品；M8-a 让站内内容第一次可被搜到；
2. **再铺底座**——M8 的统一检索 service 是 M9 与 MCP 搜索工具的共同底座，晚做等于 M9 与 MCP 各写一套口径（M6 返工登记即由此而来）；
3. **体量最大、外部不确定性最高的放并行**——M7 受平台侧影响最重，却不阻塞 M9；
4. **需要外部凭据的最后做**——M9 等用户给定 LLM/embedding 供应商与密钥再开工，避免做到半程卡在凭据上。
